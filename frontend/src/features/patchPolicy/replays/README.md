# Patch-policy reference replays

Each `.json` here is one whole output of LoonVD's patch-policy replay, copied byte for byte.
LoonInspect draws these files and computes nothing in them (#614, first slice).

Since the day-walk page (2026-11-24) these files are the page's **fallback**: they are drawn only
when no copy of LoonSec's patch-policy data answers for the organization, under a sentence that says
why ([docs/patch-policy.md](../../../../../docs/patch-policy.md); troubleshooting.md §22 step 11).
They stay until that data is live in production, so the page is never blank between a release and
the data reaching an instance.

## The stops, and the count the page reads

The page's slider has eight stops, `0d`, `1d`, `3d`, `7d`, `14d`, `30d`, `60d` and `never`, and a
stop's label is the days it waits (ruled 2026-11-27, "0 = same day"): the 0-day stop installs a
release on the date the file's timeline gives it, the 1-day stop the day after, the 3-day stop three
days after. The page reads **schema 3**, the replay that counts this way: it carries a row under
`policies` for each of the eight stops (and the tabled `critical_or_kev`, which it never draws), and
each of the seven day rows states the days it waits as `install_delay_days`, which must be the
number in its stop's id (`7d` waits 7). A file whose day row does not say so, or says otherwise, is
refused whole. A **schema-2** file counts the old way: its N-day row is N − 1 days waited, as its
own `definitions.install` says (the install date is the release date + (D − 1) days), so drawn under
these stops each number would sit a day early. The page refuses a schema-2 file whole, in words
(troubleshooting.md §22 step 4), and never relabels or recomputes one: LoonSec writes the replays.

**The four files listed below are schema 2, on the old count, and the page refuses each.** Until
they are replaced, the fallback is that refusal, one app at a time, never a drawing. Their schema-3
replacements, on the new count with each day row's delay stated, are owed from LoonVD-Internal#151,
which writes all four again; when they land, they replace these files and their rows in the table
below.

A replay names its own release dates: its `timeline` block says which public release record the
dates come from, where that record is, when it was fetched, its SHA-256, and what one of its dates
means. The page prints that block as it stands under *Evidence › Release dates*. Every replay counts
each CVE from its NVD publication date (the file's `cve_clock` is `published`, which
`clocks.published` defines), and the page says so under *Evidence › CVE clock*. The page refuses a
file on any other CVE clock, because its words state this one.

One row per file, and one file per row: `replay.test.ts` fails when an indexed file has no row
here, when a row names a file that is not indexed or is listed twice, and when a row's Bytes or
SHA-256 is not the file's. The columns:

- **Release dates from** is the file's `timeline.name`, with `timeline.url` as its link.
- **What a date means** is the file's `timeline.clock`, as the file words it.
- **CVE clock** is the file's `cve_clock`: NVD's publication date for every file here, and the
  only clock the page reads.
- **Generated by** is the LoonVD-Internal commit, and the command, that wrote the file: below.
- **Bytes** and **SHA-256** are the file's, as copied here.

### Generated by

Every file was written by LoonVD-Internal's `loonvd patch-policy` against NVD's records as LoonVD
held them on 2026-11-24, its newest change hour 22:00 UTC; a later run reads later NVD records and
can differ. The commits named here are on LoonVD-Internal branches that are **not merged** at this
writing. When they land, cite the merged commit here instead. Each file's two runs of the
generator below wrote the same bytes; a run of the merged commit against the same NVD records is
expected to write them too if the branches merge as the local merge below did, and the files are
written again from that commit if they do not.

The generator is a local merge, not pushed, of three LoonVD-Internal branches:
`claude/patch-policy-public-timeline`, which holds the engine,
`claude/patch-policy-vendor-timelines`, which holds Chrome's and Wireshark's release tables and
Chrome's promotion rows, and `claude/patch-policy-mozilla-channels`, which holds Mozilla's
release tables and the edition rule they are read with.

- **A** (all four files): the three at `123ed6d9`, `f51825c2` and `b0e48754`; the last of them
  holds the first.

## Adding or replacing one

1. Copy the new output here without editing it, and delete the file it replaces. The name is
   `<app>-<window end>.json`, the window end being the file's `window.until`.
2. Add or update its entry in `../replayIndex.ts`: the app's name, the one bundle ID the file
   replays (`product.device_bundle_id`), the file's name, and a `load` that imports that file.
3. Add or update its row in the table above, from the file's own `timeline` block and its bytes,
   and its generator under *Generated by*.
4. Update its numbers in `SHIPPED` in `../replay.test.ts` from the file, so the change shows every
   number that moved. Replacing the four schema-2 files with schema-3 ones also flips the tests that
   hold them refused as the old count (in `../replay.test.ts`, `../ReplayView.test.tsx` and
   `../PatchPolicyPage.test.tsx`; each says what to bring back), and moves the paragraph above that
   lists them as owed.
5. Run `npm test`. `replay.test.ts` reads every indexed file through the same check the page
   uses and holds what the page makes of it: while the four schema-2 files ship, that each is
   refused as the old count; once they are replaced, that each reads clean, so a file of another
   `kind` or `schema` (schema 2 among them), one whose day row does not state `install_delay_days`
   as its stop's number, one on another CVE clock, one that names no release-date source, or one
   whose totals disagree fails there and not in front of a reader. It also fails a file that
   carries a Jamf or Fleet key, or names either as its source.

This directory is how the files reach the page for this slice only. The distribution from
LoonVD through LoonSupport is not designed here.
