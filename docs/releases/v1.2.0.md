# LoonInspect v1.2.0: release notes

Status: **draft for the v1.2.0 tag**. This file becomes the body of the v1.2.0 GitHub release:
at the tag, everything below the rule is the release's description, and `release.yml` then
appends the upgrade notes beneath it. The verdicts under *Feature flags at v1.2.0* were ruled on
2026-11-19 (#813), and the two switches added after that on 2026-11-20; the lines marked
*(filled in at the tag)* are filled in then ([the convention](README.md)).

---

LoonInspect's second minor release, cut from `main` ahead of v2.0.0, a few days of work after
v1.1.0. **Read the update check's section before you update:** from this release an instance
asks LoonSec's update service, not GitHub, whether a newer release exists, about once a day and
whether or not anyone opens it, and running instances are counted from that request. The request
is five keys, with no instance identifier and no inventory, and `UPDATE_CHECK=false` still asks
nothing. The rest is small: one feature on the device page, the version history of the Fleet
catalog's titles behind its flag, a rule that keeps the catalogue of published requirements
read, and a draft release that says what it still owes. Two migrations run, one setting is
added that no operator sets, and every preview stays off.

## What ships

### The update check asks LoonSec, and says what it sends (#819)

- **Who is asked, and when.** The check now runs from the scheduler. Its first request is owed
  at a moment drawn at random within 24 hours of the first start, or of the update to this
  release; each later one 20 to 23 hours after the last answer; one that gets no answer is
  asked again an hour later. It is one `POST` to `https://api.next.loonsec.io/v1/update`, the
  production service on its interim name. Until v1.1.0 the check asked GitHub, and only while
  someone signed in had the app open.
- **What is sent: five keys and no others.**
  `{"contract":"v1","release":"v1.2.0","kind":"container","stage":"collecting","last":20776}`.
  `kind` is `container` or `mac-app`. `stage` is one word for the whole instance, how far setup
  has got: `unclaimed`, `claimed`, `connected` or `collecting`. `last` is the day number the
  previous answered check was given, and is absent before the first. Nothing about the fleet is
  in it: no device, no application, no count.
- **Running instances are counted from it** (ruled on 2026-11-19, #819). Every instance that was
  answered yesterday sends the same `last`, which is how the service counts an instance once a
  day, a week and a month with no identifier. What LoonSec keeps, and what it never receives, is
  in [the README](https://github.com/LoonSecIO/LoonInspect/blob/v1.2.0/README.md), under
  *Update notifications*.
- **The switches, and no new one.** `UPDATE_CHECK=false` asks nothing, as before.
  `UPDATE_CHECK_URL=https://api.github.com/repos/LoonSecIO/LoonInspect` keeps the notice of new
  releases, asked as v1.1.0 asked it, and the instance is not counted.
- **Said before it is sent.** The README prints the request. Settings › Support › Updates shows,
  word for word, the body the last check sent and the one the next will carry, who is asked and
  when the next check is owed. The setup page says it beside the sharing choice. On an updated
  instance whose check asks LoonSec, administrators are told in a notice that links the Updates
  block and stays until one of them dismisses it, for everyone. The container's log names the
  host at startup: *update check on: it asks api.next.loonsec.io once a day; UPDATE_CHECK=false
  turns it off*.
- **What "available" means now.** A newer release is one whose number is higher than this
  build's. No commit is compared on this provider, so *GitHub does not know this build's
  commit* cannot arise on it.
- **An egress allowlist** needs `api.next.loonsec.io:443` for the check. `api.github.com` is no
  longer asked by it; the Fleet catalogue check still asks GitHub while its flag is on.
- **An `UPDATE_CHECK_URL` that cannot be asked says so** (#832): a value that is not an address,
  names no host, or has a port no host has reads *unreachable*, sends nothing, and logs a
  warning at each attempt that names the setting and what is wrong with it, without quoting
  the value.

### LoonInspect.app checks for updates (#820)

- The app no longer starts with the check off. It asks as a container does and sends
  `"kind":"mac-app"`. It runs only while it is open and the Mac is awake, so it checks on the
  days it is used; nothing wakes it to check.
- **LoonInspect › Check for Updates Daily** is the app's switch: on by default, kept in the app's
  preferences, and applied at once (the local service restarts, in about a second). Off, the app
  asks nothing.
- When a newer release exists, the notice and Settings › Support › Updates print the app's own
  steps (quit, open the newer disk image, drag LoonInspect onto Applications, open it) and link
  the release's page, where the disk image is. They no longer print the container's commands.
- Help › Using LoonInspect on This Mac says what the request carries and where the switch is.

### Device history: the previous different value (#617)

- On a Mac's page, each value in **Device history** now opens a small detail on hover, on
  keyboard focus or at a tap. It names the newest earlier recorded state whose value differs
  from the value at the selected state, with that value and the time the Mac reported it.
  **Select this observation** moves the timeline, the values, *What moved* and the evidence to
  it, on whichever page of the timeline holds it.
- States that read the same in between are skipped. A state whose evidence is missing is shown
  as missing, never as zero and never as unchanged. When no earlier value differs in retained
  history, the detail says so and offers nothing to select.
- The lookup is the server's and reads recorded evidence and retained assessments only, never
  today's corpus. It reads at most 200 earlier states: when that bound stops it, the detail
  says how many it read, and paging back with *Older* reads further
  ([device-history.md](https://github.com/LoonSecIO/LoonInspect/blob/v1.2.0/docs/device-history.md)).

### The Fleet catalog reads each title's version history (#838)

Behind the `fleet_maintained_apps` flag, which still ships off
([fleet-catalog.md](https://github.com/LoonSecIO/LoonInspect/blob/v1.2.0/docs/fleet-catalog.md#version-history)).

- **Every version Fleet's catalog carried, and the day it took each.** Fleet's repository has
  one commit per change to a title's manifest. The instance reads the manifest at each one, so
  a title's history no longer starts on the day this instance first read it. A title's name on
  **Devices › Applications › Fleet catalog** opens its history, newest first, each date linked to
  its commit. *Version last moved* shows the history's date for the latest version and the
  version it replaced. These are the dates Fleet's catalog took each version, hours after
  Homebrew and the vendor, not release dates.
- **Slow on purpose, and only for the titles installed here.** The background reads one title
  at a time, at least two minutes apart, and only titles on a Mac in an organization with the
  flag on, most-installed first. It reads a title again only after its version moves, and only
  from where it stopped. It never spends GitHub's last 20 requests of the hour, so the daily
  check and every other tool behind the same address keep theirs. **Read history** on a title
  reads any title's whole history at once, for an account that may run **Check now**.
- **A version is dated only where the commits show it arriving.** A version the read cannot see
  arrive is left out, never given a guessed date, and the title's history says why. A failed
  read marks nothing read and sets that title aside for an hour, so the rest are still read.
- **Each instance reads for itself.** Nothing is collected by LoonSec or shipped in the image:
  the files are under Fleet's `ee/` licence, and reading them stays each operator's question,
  as with the daily check.

### Published requirements are read again at every release (#809, #736)

- A patching rule can start from a published requirement, and the entry it starts from says on
  which day its numbers were read from the publisher's own text. Until now nothing read that
  text again. From this release on, every entry is re-read before a release is tagged, and CI
  refuses a pull request that prepares a release while an entry was last read on or before the
  day of the previous release
  ([BRANCHING.md §1.1](https://github.com/LoonSecIO/LoonInspect/blob/v1.2.0/docs/BRANCHING.md#11-release-planning-milestones-labels-and-tags),
  [jamf-patch-matching.md §8c](https://github.com/LoonSecIO/LoonInspect/blob/v1.2.0/docs/jamf-patch-matching.md)).
- **This release's re-read.** *Cyber Essentials: Requirements for IT Infrastructure* v3.3 (NCSC,
  April 2026), Security Update Management, was read again on 2026-11-18 and says what the entry
  says: 14 days from release for updates that fix vulnerabilities the vendor calls critical or
  high risk, that score 7 or above on CVSS v3, or whose severity the vendor does not state, with
  14 days for every update recommended and not required. NCSC put a second copy of v3.3 up on
  2026-11-05 and links it as the current version. Its text is the first copy's, word for word,
  so the entry's link moved to it and nothing else changed. The rule editor shows the new read
  date.
- The catalogue still holds that one entry. PCI DSS v4.0.1 Requirement 6.3.3 waits for somebody
  who holds the standard to read it (#810).

### For whoever builds or releases this repository (#811, #821, #829)

- **A draft release says what it still owes** (#811). The run that makes the draft now writes
  the release commit into the notes itself, lists every line of the notes still marked to be
  filled in at the tag, and says whether `Publish images` has built that commit, with the
  command to run when it has not. A release published with a marked line still in its body
  fails its publication check, which names the lines; a published release's notes can still be
  edited. v1.1.0 was published with two such lines unfilled. At each of the last three
  publications the release commit had no images of its own: the first failed on it, and the
  next two needed `Publish images` run by hand first.
- **Stacks started for a test are not counted as installs** (#821). Everything this repository
  starts for a test sets `UPDATE_CHECK=false`, a CI job (*Test stacks uncounted*) fails a
  workflow, script or compose file that starts the image with neither that nor an
  `UPDATE_CHECK_URL` off LoonSec's production hosts, and `ops/aws/pod.template.yml` takes
  `UpdateCheckUrl`. A stack you start for a drill is yours to keep out of the count the same
  way.
- **The Mac build reads its source from a file** (#829). With a clean-tree build, `git archive`
  piped into `tar` was now and then killed by a broken pipe, which failed the build with exit
  141 and no message.

## Updating from v1.1.0 (the container)

1. **Back up first**: the dump and `ENCRYPTION_KEY`
   ([operations.md §1–2](https://github.com/LoonSecIO/LoonInspect/blob/v1.2.0/docs/operations.md)).
2. **Decide about the update check before you take the release.** Left as it is, the updated
   instance asks `api.next.loonsec.io` within its first 24 hours and about once a day after
   that, and is counted as a running instance by release, kind and setup stage. To ask nothing,
   put `UPDATE_CHECK=false` in `.env` first. To keep the notice of new releases and not be
   counted, put `UPDATE_CHECK_URL=https://api.github.com/repos/LoonSecIO/LoonInspect` there. If
   an egress allowlist stands between the container and the internet, add
   `api.next.loonsec.io:443`.
3. **Take the release.** `git fetch --tags && git checkout v1.2.0`, then build it with
   `GIT_SHA=$(git rev-parse --short HEAD) docker compose up -d --build`. Or, on an install that
   pulls, set `LOONINSPECT_VERSION=v1.2.0` in `.env` after the checkout, then
   `docker compose pull && docker compose up -d`.
4. **Two migrations run** as the new image starts. The first adds one table,
   `update_check_state`, one row holding when the next check is owed and the last answer, and
   records in `schema_release` that v1.1.0 or later can read the schema. The second adds the
   Fleet catalog's version history: one table, `fleet_app_versions`, empty until the flag is on,
   and columns on the catalog's two tables that v1.1.0 does not read. Nothing else changes, so
   the v1.1.0 image can still read the database afterwards (*Rolling back*). `docker-compose.yml`
   passes the settings it passed in v1.1.0. Sharing, the stored credentials, the feature flags
   and the signed-in sessions carry over as they are.
5. **If the check is left asking LoonSec, administrators are told** that it now does, in a
   notice on every page with a link to Settings › Support › Updates, where the request is
   shown word for word. It stays until one administrator dismisses it, which dismisses it for
   all of them. An instance that took either setting in step 2 is not shown it, unless the
   check is later pointed at LoonSec.

An update from v1.0.0 is v1.1.0's update, with its thirteen migrations and its decision about
sharing: read [the v1.1.0 notes](https://github.com/LoonSecIO/LoonInspect/releases/tag/v1.1.0)
first.

## Updating LoonInspect.app from 1.1.0

There is no updater in the app: an update is the newer disk image, taken by hand. From 1.2.0 the
app says when one exists.

1. **Quit LoonInspect** (the menu, or ⌘Q). Closing the window is not quitting.
2. **Open `LoonInspect-1.2.0-arm64.dmg` and drag LoonInspect onto Applications**, replacing the
   1.1.0 app.
3. **Open it.** The data directory and the three keychain items are the ones 1.1.0 used, so
   accounts, connections, settings and the signed-in session carry over. Two migrations run, the
   same two the container runs.

**1.2.0 checks for updates, and 1.1.0 did not.** Check for Updates Daily is on when 1.2.0 first
opens, so the app asks LoonSec's update service within its first 24 hours of running and is
counted. To ask nothing, untick **LoonInspect › Check for Updates Daily**; to be certain no
request is ever sent, set the choice before the first launch with
`defaults write io.loonsec.looninspect CheckForUpdatesDaily -bool false`.

To step back, quit and put the 1.1.0 app back
([macos-app.md](https://github.com/LoonSecIO/LoonInspect/blob/v1.2.0/docs/macos-app.md),
"Updates"). It starts without migrating, as the container's v1.1.0 image does.

## Rolling back

**To v1.1.0 it is an image swap**
([operations.md §5](https://github.com/LoonSecIO/LoonInspect/blob/v1.2.0/docs/operations.md)).
Check out `v1.1.0` and start it on the same volumes, or set `LOONINSPECT_VERSION=v1.1.0` and
pull. v1.2.0's first migration records that v1.1.0 or later can read the schema, so the v1.1.0
image finds a revision it does not carry, reads that record, and says *…so it starts without
migrating*. The `update_check_state` table and the version history stay, unread, and v1.1.0
asks GitHub as it always did. Never edit `alembic_version` or `schema_release` to make an image start.

**The Mac app, to 1.1.0, is an app swap**, and starts the same way.

**To v1.0.0 it is the downgrade**, and it has to be run from the v1.2.0 image: it is the only
one that carries v1.2.0's revision, and it carries every revision below it too. The command is
the one [the v1.1.0 notes](https://github.com/LoonSecIO/LoonInspect/releases/tag/v1.1.0) give,
`alembic downgrade f526e8b3d901`, which from this image takes v1.2.0's two steps and then
v1.1.0's thirteen. The v1.1.0 image cannot run it on a database v1.2.0 migrated. Only v1.2.0's
own steps were walked for this release.

## Known limitations

- **The published images are private, and this repository is public.** A pull needs a GitHub
  account the project has given read access to the two images; an anonymous
  `docker compose pull` is refused. Building from source needs no sign-in.
- **The update check's service runs on an interim name**, as sharing's does.
  `api.next.loonsec.io` is the production service; `api.loonsec.io` is not yet. A v1.2.0 build
  asks the interim name for as long as it runs.
- **While a check goes unanswered, a newer release already known is not announced.** The status
  reads *unreachable* or *refused* until the next answered check, an hour or more later; the
  release last named is kept and the notice returns with the answer.
- **The setup page's sentence about the update check is the same whether the check is on or
  off**: the page is read before anyone has signed in and is told nothing about settings.
- **An administrator made from `INITIAL_ADMIN_EMAIL` at a `.local`, `.test` or other
  special-use name cannot sign in** (#815): the start accepts the address and sign-in refuses it.
  Use an address at an ordinary domain. This is in v1.1.0 and v1.0.0 too.
- **The catalogue of published requirements has one entry.** A requirement enters it only once
  its publisher's own text has been read (#736, #810).
- **Jamf Pro computers only.** Apple mobile devices are future work (#616); other MDMs are outside
  this release.
- **The Mac app has no updater, no `pg_dump`, and runs only while it is open**
  ([macos-app.md](https://github.com/LoonSecIO/LoonInspect/blob/v1.2.0/docs/macos-app.md), "What
  it leaves out").
- **A promotion is a contribution without a status**, and **the Fleet catalogue is read from
  GitHub without a credential**, as in v1.1.0.
- **Unchanged from v1.1.0:** KNOWN_ISSUES.md §1 to §9. §10, the Mac app, now says the app checks
  for updates.
