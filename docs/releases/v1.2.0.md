# LoonInspect v1.2.0: release notes

Status: **draft for the v1.2.0 tag**. This file becomes the body of the v1.2.0 GitHub release:
at the tag, everything below the rule is the release's description, and `release.yml` then
appends the upgrade notes beneath it. The verdicts under *Feature flags at v1.2.0* were ruled on
2026-11-19 (#813); the lines marked *(filled in at the tag)* are filled in then
([the convention](README.md)).

---

LoonInspect's second minor release, cut from `main` ahead of v2.0.0, a few days of work after
v1.1.0. It is small on purpose: one feature on the device page, a rule that keeps the catalogue
of published requirements read, and a draft release that says what it still owes. No migration
runs, no setting is added, and every preview stays off.

Release commit: *(filled in at the tag)*.

## What ships

### Device history: the previous different value (#617)

- On a Mac's page, each value in **Device history** now opens a small detail on hover, on
  keyboard focus or at a tap. It names the newest earlier recorded state whose value differs
  from the value at the selected state, with that value and the time the Mac reported it.
  **Select this observation** moves the timeline, the values, *What moved* and the evidence to
  it, on whichever page of the timeline holds it.
- States that read the same in between are skipped. A state whose evidence is missing is shown
  as missing, never as zero and never as unchanged. When no earlier value differs in retained
  history, the detail says so and offers nothing to select.
- The lookup is the server's and reads recorded evidence and retained assessments only, never
  today's corpus. It reads at most 200 earlier states: when that bound stops it, the detail
  says how many it read, and paging back with *Older* reads further
  ([device-history.md](https://github.com/LoonSecIO/LoonInspect/blob/v1.2.0/docs/device-history.md)).

### Published requirements are read again at every release (#809, #736)

- A patching rule can start from a published requirement, and the entry it starts from says on
  which day its numbers were read from the publisher's own text. Until now nothing read that
  text again. From this release on, every entry is re-read before a release is tagged, and CI
  refuses a pull request that prepares a release while an entry was last read on or before the
  day of the previous release
  ([BRANCHING.md §1.1](https://github.com/LoonSecIO/LoonInspect/blob/v1.2.0/docs/BRANCHING.md#11-release-planning-milestones-labels-and-tags),
  [jamf-patch-matching.md §8c](https://github.com/LoonSecIO/LoonInspect/blob/v1.2.0/docs/jamf-patch-matching.md)).
- **This release's re-read.** *Cyber Essentials: Requirements for IT Infrastructure* v3.3 (NCSC,
  April 2026), Security Update Management, was read again on 2026-11-18 and says what the entry
  says: 14 days from release for updates that fix vulnerabilities the vendor calls critical or
  high risk, that score 7 or above on CVSS v3, or whose severity the vendor does not state, with
  14 days for every update recommended and not required. NCSC put a second copy of v3.3 up on
  2026-11-05 and links it as the current version. Its text is the first copy's, word for word,
  so the entry's link moved to it and nothing else changed. The rule editor shows the new read
  date.
- The catalogue still holds that one entry. PCI DSS v4.0.1 Requirement 6.3.3 waits for somebody
  who holds the standard to read it (#810).

### A draft release says what it still owes (#811)

For whoever cuts a release of this repository. The run that makes the draft now writes the
release commit into the notes itself, lists every line of the notes still marked to be filled
in at the tag, and says whether `Publish images` has built that commit, with the command to run
when it has not. A release published with a marked line still in its body fails its publication
check, which names the lines; a published release's notes can still be edited. v1.1.0 was
published with two such lines unfilled. At each of the last three publications the release
commit had no images of its own: the first failed on it, and the next two needed
`Publish images` run by hand first.

## Updating from v1.1.0 (the container)

1. **Back up first**: the dump and `ENCRYPTION_KEY`
   ([operations.md §1–2](https://github.com/LoonSecIO/LoonInspect/blob/v1.2.0/docs/operations.md)).
2. **Take the release.** `git fetch --tags && git checkout v1.2.0`, then build it with
   `GIT_SHA=$(git rev-parse --short HEAD) docker compose up -d --build`. Or, on an install that
   pulls, set `LOONINSPECT_VERSION=v1.2.0` in `.env` after the checkout, then
   `docker compose pull && docker compose up -d`.
3. **Nothing else.** No migration runs, so the instance is back as soon as the new image is
   healthy, and `docker-compose.yml` passes the settings it passed in v1.1.0. Sharing, the
   stored credentials, the feature flags and the signed-in sessions carry over as they are.

An update from v1.0.0 is v1.1.0's update, with its thirteen migrations and its decision about
sharing: read [the v1.1.0 notes](https://github.com/LoonSecIO/LoonInspect/releases/tag/v1.1.0)
first.

## Updating LoonInspect.app from 1.1.0

There is no updater in the app: an update is the newer disk image, taken by hand.

1. **Quit LoonInspect** (the menu, or ⌘Q). Closing the window is not quitting.
2. **Open `LoonInspect-1.2.0-arm64.dmg` and drag LoonInspect onto Applications**, replacing the
   1.1.0 app.
3. **Open it.** The data directory and the three keychain items are the ones 1.1.0 used, so
   accounts, connections, settings and the signed-in session carry over, and no migration runs.

To step back, quit and put the 1.1.0 app back
([macos-app.md](https://github.com/LoonSecIO/LoonInspect/blob/v1.2.0/docs/macos-app.md),
"Updates").

## Rolling back

**To v1.1.0 it is an image swap**
([operations.md §5](https://github.com/LoonSecIO/LoonInspect/blob/v1.2.0/docs/operations.md)).
Check out `v1.1.0` and start it on the same volumes, or set `LOONINSPECT_VERSION=v1.1.0` and
pull. v1.2.0 adds no migration, so the v1.1.0 image finds the schema it left. Never edit
`alembic_version` or `schema_release` to make an image start.

**The Mac app, to 1.1.0, is an app swap.**

**To v1.0.0 it is still the downgrade** the v1.1.0 notes describe, run from the v1.1.0 or the
v1.2.0 image.

## Known limitations

- **The published images are private, and this repository is public.** A pull needs a GitHub
  account the project has given read access to the two images; an anonymous
  `docker compose pull` is refused. Building from source needs no sign-in.
- **An administrator made from `INITIAL_ADMIN_EMAIL` at a `.local`, `.test` or other
  special-use name cannot sign in** (#815): the start accepts the address and sign-in refuses it.
  Use an address at an ordinary domain. This is in v1.1.0 and v1.0.0 too.
- **The catalogue of published requirements has one entry.** A requirement enters it only once
  its publisher's own text has been read (#736, #810).
- **Jamf Pro computers only.** Apple mobile devices are future work (#616); other MDMs are outside
  this release.
- **The Mac app has no updater, no `pg_dump`, and runs only while it is open**
  ([macos-app.md](https://github.com/LoonSecIO/LoonInspect/blob/v1.2.0/docs/macos-app.md), "What
  it leaves out").
- **A promotion is a contribution without a status**, and **the Fleet catalogue is read from
  GitHub without a credential**, as in v1.1.0.
- **The service runs on an interim name.** `api.next.loonsec.io` is the production service;
  `api.loonsec.io` is not yet.
- **Unchanged from v1.1.0:** KNOWN_ISSUES.md §1 to §10.

## Release validation

Recorded at the tag *(filled in at the tag)*: the release commit's CI run and test counts, and
a pull and start of the published images on a host signed in to `ghcr.io`.

Walked before the tag, on 2026-11-18, on one Apple-silicon Mac (macOS 27.3, Docker 29.6.1,
Compose 5.3.0), from the candidate at `3bb09dba` (#812). The image and the app walked were built
from a merge of the same branches whose backend, frontend, Dockerfile and `macos/` are
identical to that commit's, and the commits after it change documents only:

- **The container, from the images v1.1.0 published.** A compose project of its own ran the two
  images the v1.1.0 release tagged, pulled by that tag, beside a stand-in Jamf Pro tenant: the
  test suite's `jamf_fake.py` behind a real socket, with twelve Macs. Through the API it got an
  administrator, a sweep of the twelve, the `jamf_patch` and `app_promotion` flags, the `keys`
  tier with an exclusion, one promoted title, a webhook destination with a stored secret, and a
  patching rule confirmed from the Cyber Essentials entry. Its exchange went to LoonSec's
  development collector, never the production one: the collector stored it (94 application
  rows, two OS rows, two hardware rows and the promoted title's definition), and the reply's
  corpus had Posture › Vulnerabilities answering as of 2026-11-18. Then three changes on one Mac
  in the stand-in tenant, each swept, so that it had a history, and a dump. Two earlier
  candidates of this release were walked up and back on the same volumes first; the figures
  below are the last pass's.
- **The update.** The candidate's image on the same volumes: healthy in 2.1 s, no migration run,
  the schema's release record as it was. The session v1.1.0 minted was still signed in. Of 56
  answers read before and after, 51 were the same. The five that differed were two clocks, the
  update check (the candidate's commit is not one GitHub knows), and the catalogue entry's link
  and read date, in the catalogue and under the confirmed rule, which was still *Drawn from*
  Cyber Essentials.
- **Reporting after the update.** The firewall was turned back on on one Mac in the stand-in
  tenant and the fleet swept: fourteen events reached the destination with its stored secret
  (one `device.change`, twelve `device.inventory` and one `run.completed`). The exchange was
  sent with the candidate's build string, and the collector stored it. At its scheduled minute
  the scheduler found the daily sweep due and skipped it inside its rate floor, a manual sweep
  having run half an hour before.
- **The new detail, in a browser** (Chromium). Signed in as a viewer, on a Mac with six
  recorded states: *Operating system: 14.7* opened *Previously: 14.6.1* with the Mac's report
  time; **Select this observation** pressed that state's dot and moved the focus to it, the
  card read *Historical*, and the six values changed with it. Keyboard focus on *FileVault*
  opened *No earlier different value in retained history*, and Escape closed it with the focus
  still on the value. Safari's engine, which the Mac app's window also uses, was exercised by
  the pull request's review in a WebKit harness, not here; a touch screen and a screen reader
  were not tried.
- **The step back.** The published v1.1.0 image on the database the candidate had used: healthy
  in 2.1 s and still signed in, with 51 of 56 answers as the candidate gave them and the other
  five the clocks, the update check and the catalogue entry's two fields, which read as v1.1.0
  has them. A sweep under it succeeded, and the candidate put back afterwards started as before. **v1.2.0 adds no
  migration, so this did not exercise the schema's release record**: the v1.1.0 image found its
  own head.
- **The release record, exercised apart from the release.** On a second throwaway stack, with
  two builds made only for this walk, each the candidate's tree plus one synthetic migration.
  After the one that records that v1.1.0 or later can read the schema, the published v1.1.0
  image started without migrating and said *…which recorded that v1.1.0 or later can read it;
