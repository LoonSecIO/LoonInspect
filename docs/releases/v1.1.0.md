# LoonInspect v1.1.0: release notes

Status: **draft for the v1.1.0 tag**. This file becomes the body of the v1.1.0 GitHub release:
at the tag, everything below the rule is the release's description, and `release.yml` then
appends the upgrade notes (the thirteen migrations since v1.0.0) beneath it. The verdicts under
*Feature flags at v1.1.0* were ruled on 2026-11-15; the lines marked *(filled in at the tag)*
are filled in then.

---

LoonInspect's first minor release, cut from `main` ahead of v2.0.0. It is everything merged
since v1.0.0 with every preview left off: a Mac app, a second sign-in factor, a PostgreSQL you
run, published images, a schema that records which releases can read it, retention and key
rotation, and two new areas behind feature flags, promoted applications and Fleet's
maintained-apps catalogue.

Release commit: *(filled in at the tag)*.

## What ships

### New in this release, both behind feature flags and off

- **Promoted applications** (#793, flag `app_promotion`). The service learns an application's
  name only once five organizations report it, and that rule is paused. With the flag on, an
  administrator promotes an installed application under Settings › Data Sharing, and each
  exchange then carries that title's name, bundle ID and versions in plain text beside the
  hashes it already sent. Only what is promoted is sent by name, the exclude list wins, the
  preview and the share log show the rows, and a `413` sheds them before anything else. Off,
  the exchange is byte for byte what it was.
  [data-sharing.md](https://github.com/LoonSecIO/LoonInspect/blob/v1.1.0/docs/data-sharing.md#promoted-applications)
  is the contract. What LoonSec's service does with a promoted definition is the service's work
  and is not part of this release.
- **Fleet's maintained-apps catalogue** (#794, flag `fleet_maintained_apps`). With the flag on,
  the instance reads Fleet's public catalogue of Mac apps from GitHub once a day and Devices ›
  Applications gains a **Fleet catalog** tab: each Fleet title this organization has installed,
  Fleet's latest version, how many Macs have it and how many are behind. Off, no request is
  made. The catalogue's files sit under Fleet's `ee/` licence, which says production use needs
  a Fleet subscription: read
  [fleet-catalog.md](https://github.com/LoonSecIO/LoonInspect/blob/v1.1.0/docs/fleet-catalog.md)
  before turning it on.

### LoonInspect.app for macOS (#783, #790, #791)

- One app, one Apple-silicon Mac, macOS 13 or later: the same backend, frontend and PostgreSQL
  17 the container runs, as child processes of a small native shell. The data is in
  `~/Library/Application Support/LoonInspect`, the secrets in the login keychain.
- This is the first release with the app attached: `LoonInspect-1.1.0-arm64.dmg`, a ZIP and
  `SHA256SUMS`, built from the release commit, signed with a Developer ID, notarized by the
  `macOS release` workflow, and put on this release while it was still a draft.
- It runs while it is open and the Mac is awake. A fleet whose events must reach a SIEM every
  night runs the container
  ([macos-app.md](https://github.com/LoonSecIO/LoonInspect/blob/v1.1.0/docs/macos-app.md),
  [KNOWN_ISSUES.md §10](https://github.com/LoonSecIO/LoonInspect/blob/v1.1.0/KNOWN_ISSUES.md)).

### Two-step sign-in (#653)

- A local account adds an authenticator-app code (TOTP) under *Two-step sign-in* on My Account,
  with ten one-use recovery codes.
- Settings › Accounts sets who must have one: nobody (the default), administrators, or everyone.
  The break-glass account is never asked. An administrator can remove another account's second
  factor.
- The audit log records enrolment, refused codes, recovery-code use and replacement, removal and
  policy changes.

### A PostgreSQL you run (#654)

`DATABASE_MODE=external` with `docker-compose.external.yml` runs the app against your server. The
URL must ask for TLS, and before it migrates the app refuses a superuser, a `BYPASSRLS` role, or a
role that cannot create in schema `public`, each in a sentence.
[operations.md §8](https://github.com/LoonSecIO/LoonInspect/blob/v1.1.0/docs/operations.md) has
backup, restore, upgrade and rollback for this shape.

### Published images, and a schema that says which releases can read it (#655, #672)

- `ghcr.io/loonsecio/looninspect:v1.1.0` and `ghcr.io/loonsecio/looninspect-db:v1.1.0`, for
  `linux/amd64` and `linux/arm64`, are the images `main` built for the release commit, copied at
  publication, never tagged `latest`. `docker-compose.pull.yml` runs them
  ([README step 4](https://github.com/LoonSecIO/LoonInspect/blob/v1.1.0/README.md#4-build-and-run)).
  Both are private, as the repository is: a pull needs Docker signed in to `ghcr.io` as a GitHub
  account that can read the repository, and without that it stops at `unauthorized`.
- The schema records the oldest release that can read it. An image that finds a revision it does
  not carry starts without migrating when its release is at or above that record, and otherwise
  refuses in one sentence naming both releases. So once a release follows this one, stepping
  back from it to v1.1.0 is an image swap. Stepping back from v1.1.0 to v1.0.0 is not: see
  *Rolling back*.
- Each release page carries its upgrade notes: first any migration that needs a maintenance
  window or free disk, then every migration the update runs at its first start.

### Retention, key rotation and storage (#785, #144, #786)

- `CHANGE_LOG_RETENTION_DAYS` puts the change log on a clock. It is off by default: the log is
  kept for ever unless you set it.
- `ENCRYPTION_KEY` can be rotated: `ENCRYPTION_KEY_PREVIOUS` holds the old key while a rewrite
  moves every stored credential to the new one
  ([operations.md §1](https://github.com/LoonSecIO/LoonInspect/blob/v1.1.0/docs/operations.md)).
- Settings › Support has a **Storage** card: what the database holds, table by table, and the
  clock each table is on.

### Patch policy (#731, #732, #736, #614)

- The organization's stated patching policy gains confirmed rules, and the Jamf Patch page
  judges devices against them. The rule editor can draft limits from the statement, and a rule
  can start from a published requirement.
- A reference page, Posture › Patch policy, is listed with the `patch_policy` flag, off by
  default: a replay of a hypothetical Mac, not this organization's exposure.

### The exchange, and what stays as it was

- **The exchange reaches LoonSec's production collector.** `SHARING_ENDPOINT` defaults to
  `https://api.next.loonsec.io/v1/exchange`. v1.0.0's default collector address answered every
  exchange with `403`, so step 2 of *Upgrading from v1.0.0* is a decision to make before you
  update.
- **Reveals stay paused.** This build stores and answers no reveal request at any tier and drops
  any a v1.0.0 build queued. The `reveal` tier stays as set and uploads what `keys` uploads
  (#624).
- **The contribute-or-pay previews are built and off**: paid access, contribution receipts,
  tenant-selected corpus releases, and Request coverage with Report an incorrect match. See
  *What stays off*.

### Also since v1.0.0

- An extension attribute's value change is evidence for inventory summaries, gated by the Change
  Log policy (#644).
- The device page dates each event by when this instance recorded it (#645), *Findings first
  checked* carries this instance's clock (#646), and Device history pages in the direction it
  reads (#618).
- An AI share-log row names the model asked for (#739), and the Apple card uses only the
  on-device model (#738).
- `docker-compose.yml` lists every setting the app reads, each at its default under a comment
  naming the page that explains it (#707). `SYNC_TIMEZONE` names its canonical form when it
  refuses one (#713).
- Inventory ingestion is bounded and a run keeps its owner across a restart (#763); run logs
  survive polling and panel changes (#764).
- A feature-flag toggle saved while a slow listing was loading is no longer overwritten by it
  (#675).
- The audit log gains `auth.mfa.*`, `settings.mfa_policy.changed`, `intelligence.*`,
  `submission.*` and `sharing.promotion.*` actions.
- [troubleshooting.md](https://github.com/LoonSecIO/LoonInspect/blob/v1.1.0/docs/troubleshooting.md)
  has twenty-four paths, among them two-step sign-in (§20), the Mac app (§25), promoted
  applications (§26) and the Fleet catalogue (§27).

## Upgrading from v1.0.0 (the container)

1. **Back up first**: the dump and `ENCRYPTION_KEY`
   ([operations.md §1–2](https://github.com/LoonSecIO/LoonInspect/blob/v1.1.0/docs/operations.md)).
   The key stays the same, and the dump is the simplest way back.
2. **Decide about sharing before you update.** On v1.0.0's default address, `api.loonsec.io`, no
   exchange reached LoonSec: every one read `403 Missing Authentication Token`. v1.1.0 posts to
   the production collector, so an organization whose sharing is on sends its first exchange that
   arrives at its next daily run (or **Send now**), keys and install counts as its tier says, and
   the reply's corpus link is where Posture › Vulnerabilities starts answering from. Settings ›
   Data Sharing shows the literal next payload; choose **Off** before updating if it should not
   leave.
3. **Read the upgrade notes below.** Thirteen migrations run at the first start, in one
   transaction. `e621c4a8b903` rebuilds the installed-apps index while the instance answers
   nothing: a second or two on 600,000 installed apps, longer on a larger table. The migrations
   change no sharing tier, stored answer or licence value, and send nothing.
4. **Take the release.** `git fetch --tags && git checkout v1.1.0`, then build it with
   `GIT_SHA=$(git rev-parse --short HEAD) docker compose up -d --build`, which needs Docker's
   BuildKit builder (the default in Docker Desktop and Compose v2). Or pull it: sign Docker in
   to `ghcr.io` (README step 4), add `COMPOSE_FILE=docker-compose.yml:docker-compose.pull.yml`
   and `LOONINSPECT_VERSION=v1.1.0` to `.env`, then `docker compose pull && docker compose up -d`
   (Compose 2.24 or newer).
5. **Check `.env`.** v1.0.0's `docker-compose.yml` passed 29 fewer settings than this one. Nine
   are new: `INTELLIGENCE_ACCESS`, `CONTRIBUTION_RECEIPTS`, `VULN_TENANT_SELECTION`,
   `VULN_RELEASE_RETENTION`, `INTELLIGENCE_SUBMISSIONS`, `INTELLIGENCE_ENDPOINT`,
   `CHANGE_LOG_RETENTION_DAYS`, `ENCRYPTION_KEY_PREVIOUS` and `WEBHOOK_TIMEOUT_SECONDS`. The other
   twenty, among them `LOG_LEVEL`, `SYNC_TIMEZONE`, `SHARING_ENDPOINT` and the retention days,
   existed and ran at their defaults, as they still do (`SHARING_ENDPOINT`'s is step 2). A line
   for one of them in `.env`, which v1.0.0 ignored, takes effect now, and a value the app refuses
   stops the start with a sentence naming the variable
   ([troubleshooting.md §4](https://github.com/LoonSecIO/LoonInspect/blob/v1.1.0/docs/troubleshooting.md)
   step 2).

## Updating LoonInspect.app from 1.0.0

There is no updater in the app: an update is the newer disk image, taken by hand.

1. **Quit LoonInspect** (the menu, or ⌘Q). Collection and delivery stop and the database shuts
   down. Closing the window is not quitting.
2. **Open `LoonInspect-1.1.0-arm64.dmg` and drag LoonInspect onto Applications**, replacing the
   1.0.0 app.
3. **Open it.** The first launch runs the migrations, as the container's first start does. The
   data directory and the three keychain items are the ones 1.0.0 made, so accounts, connections,
   settings and the signed-in session carry over.

The app's own sharing decision is step 2 above: review Settings › Data Sharing before the first
exchange. To step back, quit and put the 1.0.0 app back: 1.0.0 was built after the schema began
recording which releases can read it, so it starts on the database 1.1.0 migrated without
migrating ([macos-app.md](https://github.com/LoonSecIO/LoonInspect/blob/v1.1.0/docs/macos-app.md),
"Updates"). A copy of `pgdata` taken while the app is quit, with the matching keychain items, is
the backup.

## What stays off, and why

**The contribute-or-pay previews** (#620) ship off, as v1.0.0 did not have them at all: paid
access under Settings › Intelligence Access, contribution receipts, and tenant-selected corpus
releases. The v2.0.0 gate ruled them *promote at the v2.0.0 tag*, once the deployed checks of
#624 are recorded. Nothing in this release turns them on, and an instance that leaves them off
makes the daily exchange v1.0.0 made, to an address that now answers.

**Request coverage and Report an incorrect match** (#623) ship with `INTELLIGENCE_SUBMISSIONS`
off, as ruled on 2026-09-27 (#692). They also need paid access on.

**Promoted applications and the Fleet catalogue** are new and off. Each is one switch under
Settings › Feature Flags, and each says on its own page what turning it on sends or fetches.

## Rolling back

**The container, to v1.0.0, is the downgrade**
([KNOWN_ISSUES.md §6](https://github.com/LoonSecIO/LoonInspect/blob/v1.1.0/KNOWN_ISSUES.md)).
The v1.0.0 image predates the schema's release record, so starting it on a database v1.1.0
migrated crash-loops on `Can't locate revision identified by '…'`. Restore the dump taken before
the upgrade beside the v1.0.0 image
([operations.md §3](https://github.com/LoonSecIO/LoonInspect/blob/v1.1.0/docs/operations.md)),
or, with v1.1.0 still running, run the downgrade to v1.0.0's head (`f526e8b3d901`) from the
v1.1.0 image first:

```bash
docker compose run --rm --no-deps app uv run --frozen --no-sync --no-dev alembic downgrade f526e8b3d901
git checkout v1.0.0
GIT_SHA=$(git rev-parse --short HEAD) docker compose up -d --build
```

- The downgrade runs in one transaction and removes what v1.1.0 added: second factors and the
  sign-in policy, confirmed patching rules, promoted applications, the Fleet catalogue, submission
  cases, the retained corpus releases with each organization's selections, and the release
  record. It rebuilds the index `e621c4a8b903` replaced, so it wants the same window.
- Once an organization has recorded assessment history (only with the tenant-selection preview
  on), it refuses: *Assessment history exists. Keep this schema or restore a pre-upgrade backup;
  downgrade would lose evidence.* The transaction takes every step back, and the dump is the way
  back.
- On an install that pulls, delete the `COMPOSE_FILE` and `LOONINSPECT_VERSION` lines from `.env`
  before the checkout: v1.0.0 has no published image and no `docker-compose.pull.yml`.
- An instance on `DATABASE_MODE=external` has no v1.0.0 to return to: v1.0.0 refuses that mode.

**The Mac app, to 1.0.0, is an app swap**, as *Updating LoonInspect.app* says.

**Back to v1.1.0 from a later release it is an image swap**, unless that release's notes say it
needs a later one ([operations.md §5](https://github.com/LoonSecIO/LoonInspect/blob/v1.1.0/docs/operations.md)).
Never edit `alembic_version` or `schema_release` to make an image start.

## Known limitations

- **Jamf Pro computers only.** Apple mobile devices are future work (#616); other MDMs are outside
  this release.
- **The Mac app has no updater, no `pg_dump`, and runs only while it is open**
  ([macos-app.md](https://github.com/LoonSecIO/LoonInspect/blob/v1.1.0/docs/macos-app.md), "What
  it leaves out"). The app does not tell you a newer release exists: watch the releases
  page.
- **A promotion is a contribution without a status.** This instance cannot see whether the
  service has used a promoted definition; coverage arrives with a published corpus release.
- **The Fleet catalogue is read from GitHub without a credential**, so GitHub's limit of 60
  requests an hour per address applies, and a shared address can meet it.
- **The service runs on an interim name.** `api.next.loonsec.io` is the production service;
  `api.loonsec.io` is not yet, and an endpoint set to it reads `403` on every request.
- **A step back to the v1.0.0 image is the downgrade above.**
- **Building from source needs BuildKit** (#716).
- **Single sign-on and WebAuthn remain future work** (#303). Two-step sign-in is TOTP on local
  accounts.
- **Unchanged from v1.0.0:** the observation ledger has no retention limit, a full database
  volume says so only in the database's log, Docker Compose does not restart a running app whose
  healthcheck fails, a wrong `ENCRYPTION_KEY` is found only when a credential is read, and the
  Overview's patch-laggards tile has a documented scaling limit (KNOWN_ISSUES.md §1–§5, §7).

## Release validation

Recorded at the tag *(filled in then)*: the release commit's CI run and test counts, and a
release candidate drafted and published the way this release is (both images tagged and copied
to ghcr.io, a pull and start from README step 4 on a host signed in to ghcr.io that built
neither image, and the notarized disk image on the release, opening under Gatekeeper on a Mac
that did not build it).

`v1.1.0-rc.1`, published on 2026-11-16, was the first run of `release.yml` and of
`macOS release` at a publication. It found two defects, which is what it was for:

- **It carries no Mac app.** The workflow built, signed and notarized the disk image, and
  GitHub then refused it: this repository's releases are immutable, and a published release
  takes no more files. The files now go onto a draft, and publishing the draft is the
  release. The disk image that run built was checked on a Mac that did not build it: its
  checksums match, the image and the app inside each carry their stapled ticket, and
  Gatekeeper reads both as *Notarized Developer ID*.
- **Its images were not there at publication.** Its commit changed only documents, and `main`
  builds images only for a commit that changes what an image is made from, so there was
  nothing for `release.yml` to tag. The same run did show the push role trusting a `v*` tag
  and the upgrade notes being written. The release procedure now says to run
  `Publish images` from `main` first when the release commit changed none of those paths.

`v1.1.0-rc.2`, published on 2026-11-17 from a draft at `86d76e54`, was the first candidate to
go through both workflows:

- **The draft carried the Mac app.** `macOS release`, run from `main` with the tag, built,
  signed and notarized the disk image and put it, the zip and `SHA256SUMS` on a draft. On a Mac
  that did not build them the sums matched, the disk image carried its stapled ticket, and
  Gatekeeper read it as *Notarized Developer ID*. After publication the workflow read the three
  files back from the release and matched them to their sums again.
- **Its images were there.** The release commit changed only a workflow, so `Publish images`
  was run from `main` before publication, as the procedure says. `release.yml` then gave both
  images the version tag, by the digests that run pushed, copied them to ghcr.io, and wrote the
  thirteen migrations and the `e621c4a8b903` window into the release's notes.
- **A pull without a sign-in was refused.** On a host with no ghcr.io sign-in (Docker 29.6.1,
  Compose 5.3.0), `docker compose pull` with README step 4's override stopped at `unauthorized`
  for both images: the packages are private, as the repository is. README step 4 and
  [troubleshooting §10](https://github.com/LoonSecIO/LoonInspect/blob/v1.1.0/docs/troubleshooting.md)
  step 4 now say what to sign in with. The pull and start signed in is among what is recorded
  at the tag.

Recorded before either, on one Apple-silicon Mac (macOS 27.3, Docker 29.6.1), 2026-11-15:

- **The container, from the v1.0.0 tag.** The v1.0.0 tree, built and started by
  `docker compose up -d --build` as a compose project of its own, was set up through its API (an
  administrator, a flag, the `keys` tier with an exclusion, a destination with a stored secret;
  `COMMUNITY_SHARING=false`, so nothing left it) and dumped. The release-prep tree at `e2300e4`
  was then built and started on the same volumes. Thirteen migrations ran in one transaction,
  `f526e8b3d901` to `f794a1c3d5e7`, in under a tenth of a second on that small database. The
  release record read `v1.0.0`, the session v1.0.0 minted was still signed in, every value
  v1.0.0 had answered was answered the same, the stored secret was read, and both new areas
  answered off.
- **The container's step back.** The v1.0.0 image started on the upgraded database without a
  downgrade and crash-looped on `Can't locate revision`, as *Rolling back* says. The downgrade to
  `f526e8b3d901`, run from the newer image, took its thirteen steps and left none of the tables
  this range adds; the v1.0.0 image then started, and every value read as before the upgrade.
- **The Mac app, 1.0.0 to 1.1.0 and back**, both built from clean trees with the Developer ID
  and installed from their disk images: healthy in 1.67 s on the same port, the two migrations
  1.1.0 adds run, the session, settings, stored secret and keychain items carried; the 1.0.0 app
  put back started without migrating and read everything as before
  ([macos-app.md](https://github.com/LoonSecIO/LoonInspect/blob/v1.1.0/docs/macos-app.md),
  "Validation (1.1.0)").
- **The two new areas, in a running instance** seeded with eight Macs: a promoted title's row in
  the previewed payload carried the `full` keys and counts of the snapshot's rows for it, an
  exclusion held it back, and withdrawing removed the key; the Fleet catalogue read 953 Mac apps
  from GitHub in one check and listed the six seeded titles Fleet maintains.
- **The test lanes on the release-prep branch**: backend, 2596 passed without a database and
  4241 passed, 71 skipped and 3 expected failures with one; the migration contract over all thirteen migrations; frontend, 60 files and 709
  tests; the README's claims; the Mac app's script tests.

Not walked here: an upgrade over real inventory (`backend/tests/test_v2_release_gate_db.py`
